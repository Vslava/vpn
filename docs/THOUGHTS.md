# THOUGHTS — Принятые решения

## Q1: Потоковое шифрование

- **Вопрос**: нужно ли шифрование в туннеле?
- **Варианты**: без шифрования (plaintext), с шифрованием (AES-GCM, ChaCha20-Poly1305).
- **Решение**: XChaCha20-Poly1305 + X25519 ECDH + PSK (256-bit). Каждый пакет — отдельный AEAD nonce. Key Exchange: hybrid (PSK + эфемерные X25519) для PFS.
- **Формулировка человека**: "Добавить потоковое шифрование"

---

## Q2: Режимы клиент/сервер

- **Вопрос**: приложение только перехватывает трафик клиента, или включает серверную часть?
- **Варианты**: только клиент, раздельные бинарники, единый бинарник с режимами.
- **Решение**: единый бинарник, два режима — `--mode server` и `--mode client`.
- **Формулировка человека**: "Приложение должно запускать как сервер и клиент"

---

## Q3: Конфигурируемый IP/порт

- **Вопрос**: адреса хардкодом или через конфиг?
- **Варианты**: хардкод в коде, переменные окружения, TOML-конфиг.
- **Решение**: `[server].listen` и `[client].remote` в TOML-конфиге.
- **Формулировка человека**: "Должна быть возможность выбора IP адреса и порта на котором будет слушать сервера и куда будет передавать клиент"

---

## Q4: Протокол инкапсуляции

- **Вопрос**: через какой протокол передавать трафик между клиентом и сервером?
- **Варианты**: IP-in-UDP, IP-in-TCP, собственный протокол поверх UDP, QUIC, Noise Protocol Framework, UDP с фреймингом.
- **Решение**: TCP-туннель (IP-in-TCP). Шифрованный payload через TCP-соединение. Риск TCP-over-TCP учтён, mitigation: TCP_NODELAY, большие буферы.
- **Формулировка человека**: "Было бы хорошо весь трафик шифровать и передавать через TCP. Так чтобы внутри TCP пакета не видно было изначальный трафик. На стороне сервера делать retransmit. Ну соответственно ответы в обратную сторону."

---

## Q5: Обработка ICMP

- **Вопрос**: что делать с ICMP-пакетами внутри туннеля?
- **Варианты**: игнорировать, обрабатывать локально, пропускать в туннель.
- **Решение**: ICMP как любой другой IP-пакет, без специальной обработки.
- **Формулировка человека**: "пропускаем в тунель"

---

## Q6: MTU

- **Вопрос**: какой MTU выставить на TUN-интерфейсе и как считать overhead?
- **Варианты**: 1500 (без изменений), 1400 с запасом, 1280 (минимальный IPv6), автоопределение.
- **Решение**: TUN MTU = 1400 (конфигурируется). Overhead: Poly1305 (16) + nonce (24) + length prefix (2) + запас ≈ 50. PMTUD через ICMP от TUN.
- **Формулировка человека**: "давай сделаем так"

---

## Q7: TUN crate

- **Вопрос**: какой крейт использовать для создания TUN-интерфейса?
- **Варианты**: `tun-rs` v2, `meh/rust-tun` v0.8, собственный ioctl.
- **Решение**: `tun-rs` v2 (современный, tokio-native, cross-platform).
- **Формулировка человека**: "давай использовать tun-rs"

---

## Q8: Права доступа

- **Вопрос**: как обрабатывать требования root/admin на разных платформах?
- **Варианты**: Linux capabilities (`setcap`), sudo, setuid, Windows UAC, macOS launchd.
- **Решение**: Linux — sudo. Windows — UAC `requireAdministrator`. macOS — sudo.
- **Формулировка человека**: "Почему нельзя выбрать два варианта в зависимости от того под что компилируется приложение ? Для Linux один подход, а под Windows другой. MacOS третий." → "Давай для Linux будет sudo"

---

## Q9: Многопоточность / очереди

- **Вопрос**: как организовать concurrency — каналы между задачами или sequential pipeline?
- **Варианты**: A — две tokio-задачи без каналов, B — три задачи с mpsc, C — multi-threaded workers, D — object pool.
- **Решение**: вариант A — две tokio-задачи (`tun_to_tcp`, `tcp_to_tun`), sequential pipeline, без каналов, tokio multi_thread.
- **Формулировка человека**: "давай вариант A"

---

## Q10: Поведение при переполнении буфера

- **Вопрос**: Drop или Block при переполнении внутреннего буфера?
- **Варианты**: Drop (терять новые пакеты), Block (ждать освобождения).
- **Решение**: Block. В sequential pipeline (Q9) это поведение по умолчанию.
- **Формулировка человека**: "Тогда Block"

---

## Q11: Nonce

- **Вопрос**: какой подход к nonce для XChaCha20 — счётчик, случайный, гибрид?
- **Варианты**: A — полностью случайный 24 байта на пакет, B — session_id + u64 counter, C — random + counter.
- **Решение**: вариант A — случайный 24-байтовый nonce на каждый пакет (CSPRNG). Overhead: 24 байта на пакет.
- **Формулировка человека**: "давай вариант A"

---

## Q12: Key rotation

- **Вопрос**: нужна ли ротация сессионного ключа внутри одного соединения?
- **Варианты**: делать (по времени/трафику), не делать.
- **Решение**: не делать. Сессионный ключ живёт до перезапуска.
- **Формулировка человека**: "давай не будем делать"
