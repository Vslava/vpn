# Skill: Составление плана проверки (Verification Plan)

## Description

Создаёт исчерпывающий план верификации для фазы или этапа реализации. План должен однозначно подтверждать или опровергать работоспособность функционала, включая краевые случаи.

## When to Use

- После того, как написан implementation plan с разбивкой на этапы
- Перед началом реализации этапа — чтобы заранее определить критерии приёмки
- Когда нужно формально подтвердить, что функционал работает

## Workflow

### 1. Определить scope

Один файл = одна фаза или один крупный этап. Если этапов много — создать отдельный файл для каждого.

Структура файла:

```markdown
# Verification Plan: <Phase Name>

## Общая информация

- **Цель**: ...
- **Среда**: ...
- **Предусловия**: ...

## <Sub-step 1>

### Проверка: <что проверяем>

```bash
<команда>
```

**Ожидаемый результат**: <конкретный вывод>

### Edge cases

| Сценарий | Действие | Ожидаемый результат |
|----------|----------|---------------------|

## <Sub-step N>

...

## Итоговый чеклист

- [ ] ...
```

### 2. Для каждого подэтапа определить:

1. **Happy path** — точная команда и точный ожидаемый вывод (не "должен работать", а `ip addr show ts0` → `inet 10.0.0.2/30`)
2. **Несколько краевых случаев** — минимум 3-5 на подэтап
3. **Негативные сценарии** — что будет, если ввод невалиден/permissions нет/сеть недоступна/компонент упал
4. **Граничные значения** — минимум (0), максимум (MTU, длина ключа, порт), пустые значения

### 3. Типы проверок (чередовать):

| Тип | Описание |
|-----|----------|
| **Unit** | Изолированная проверка одного модуля (encrypt→decrypt) |
| **Integration** | Проверка связки модулей (pipeline) |
| **System** | Полный цикл от пользовательского действия до результата |
| **Negative** | Проверка отказа (неверный ключ, нет прав) |
| **Edge** | Граничные значения (MTU, пустые данные, 0 байт) |
| **Soak** | Длительная работа (60s ping, 1000 пакетов) |
| **Resilience** | Поведение при падении компонента (kill сервера) |

### 4. Формат написания

- **Команды** — точные bash-команды, которые можно скопировать и выполнить
- **Ожидаемый результат** — конкретный текст вывода, exit code, состояние системы (`ip route`, `ip link`)
- **Таблицы edge cases** — для компактного перечисления множества сценариев
- **Чеклист в конце** — каждый пункт проверяем и отмечаем

### 5. Что обязательно должно быть покрыто

- **Permissions**: что будет без root
- **Отсутствующие ресурсы**: нет конфига, нет сервера, нет TUN
- **Битые данные**: повреждённый ciphertext, неверный nonce, мусор в сокете
- **Гонки**: сигнал во время reconnect, shutdown во время трафика
- **Очистка**: после SIGKILL — зомби-маршруты, зомби-TUN
- **Восстановление**: reconnect, restore routes
- **Производительность**: CPU, memory, throughput относительно baseline

### 6. Критерии готовности плана

- [ ] Каждый подэтап имеет хотя бы один happy path test
- [ ] Каждый подэтап имеет таблицу edge cases (≥3 записей)
- [ ] Все команды можно скопировать и выполнить (не псевдокод)
- [ ] Ожидаемый результат указан для каждого теста
- [ ] В конце есть чеклист для отметки выполнения
- [ ] Указаны предусловия (какие компоненты должны быть готовы)
